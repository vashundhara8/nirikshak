# Deficiency Compatibility Report

## Overview
This report analyzes the compatibility between the existing ground truth, the outputs generated by upstream Steps (10, 11, 12), and the newly proposed Step 13 Deficiency Intelligence Architecture. It was produced by inspecting `dataset/ground_truth/post_matric/deficiency_ground_truth.json`, `dataset/predictions/cross_validation/post_matric/validation_predictions.json`, and `dataset/predictions/policy/post_matric/policy_predictions.json`.

## 1. Existing Deficiency Ground Truth Structure
The existing ground truth relies on a flat dictionary with the following schema:
- `deficiency_id`: String (e.g., `"DEF-0001"`)
- `application_id`: String (e.g., `"APP-0021"`)
- `deficiency_type`: String (Only one type currently present in GT: `"MISSING_DOCUMENT"`)
- `severity`: String (Only one value currently present in GT: `"HIGH"`)
- `description`: String
- `affected_document_ids`: List[String]
- `affected_fields`: List[String]
- `source_rule_ids`: List[String] (e.g., `["PM-DOC-001"]`)
- `expected_action`: String (e.g., `"REQUEST_CORRECTION"`)
- `evidence_ids`: List[String]

## 2. Upstream Validation Prediction Structure
Cross-document validations are flat dictionaries:
- `application_id`: String
- `validation_type`: String (e.g., `"NAME_CONSISTENCY"`)
- `status`: String (`"PASS"`, `"FAIL"`, `"NOT_APPLICABLE"`)
- `field`: String
- `values`: List[Dict]
- `reason`: String
- `evidence`: List[Dict]

## 3. Upstream Policy Prediction Structure
Policy evaluations are grouped inside application summary objects:
- `application_id`: String
- `policy_version`: String
- `rule_evaluations`: List[Dict]
  - `rule_id`: String
  - `status`: String (`"PASS"`, `"FAIL"`, `"MANUAL_REVIEW_REQUIRED"`, `"NOT_APPLICABLE"`)
  - `reason`: String
  - `expected_condition` / `actual_value`
  - `source_reference`: Dict

## 4. Deterministic Matching Fields (For Evaluation)
To deterministically match a prediction to the ground truth without altering either, we use:
1. `application_id` (Exact match)
2. `deficiency_type` (Exact match: e.g., `"MISSING_DOCUMENT"`)
3. `rule_id` intersecting with `source_rule_ids`

## 5. Detected Semantic Conflicts and Resolutions
**Severity Taxonomy Mismatch**: 
- The Ground Truth defines Missing Documents as `"HIGH"`. 
- The new Step 13 architecture categorizes Missing Documents as `"BLOCKING"`.
- **Resolution**: As mandated, the ground truth is preserved as-is. The evaluation script matches the findings independently of severity, computes severity accuracy (which registers 0% for these cases), and explicitly reports the expected vs. predicted mismatch in the output logs.

**Missing Document Representation in Step 12**:
- The `PM-DOC-001` rule was outputting `"MANUAL_REVIEW_REQUIRED"` rather than `"FAIL"` due to Aadhaar ambiguity handling in Step 12.
- **Resolution**: To properly capture this as a Deficiency matching the Ground Truth, the Deficiency Engine explicitly processes `DOC` rules with `MANUAL_REVIEW_REQUIRED` as Deficiencies, fulfilling the ground truth requirement while routing other ambiguities correctly to Exceptions.

## 6. Unsupported Fields in Evaluation
The new architecture introduces `RerunScope`, `ResponsibleParty`, and `Exception Classification`. Since these concepts do not exist in the old `deficiency_ground_truth.json`, the evaluation script safely outputs `NOT_AVAILABLE` for their accuracy metrics, preventing fabricated labels.
